Provider 2.0 adds API keys, more merge queue settings, and fixes. Existing state loads as is, and the organization API token keeps working, so most configurations upgrade with no changes. Read [What changes](#what-changes) first: two behaviors differ from 1.x.

## Upgrade

1. Change the version constraint:

   ```hcl
   terraform {
     required_providers {
       trunk = {
         source  = "trunk-io/trunk"
         version = "~> 2.0"
       }
     }
   }
   ```

2. Run `terraform init -upgrade`.
3. Run `terraform plan`. For a configuration that sets `required_statuses`, or doesn't rely on leaving it out (see below), the plan is empty.

## What changes

### Leaving out `required_statuses` no longer removes the override

In 1.x, a configuration without `required_statuses` removed the queue's override whenever an apply updated the queue, including an override set in the Trunk app. In 2.0, leaving it out leaves the override alone.

If you relied on that to keep the override cleared, set it explicitly:

```hcl
required_statuses = []
```

`[]` removes the override, so the queue uses `.trunk/trunk.yaml` or branch protection. In 1.x, `[]` did nothing.

### `required_statuses` is a set

Order no longer matters. In 1.1.0, a list in any order but alphabetical failed the apply.

If another part of your configuration indexes into it, such as `trunk_merge_queue.main.required_statuses[0]`, wrap it in `tolist()`.

### `api_key` and `base_url` must be known when planning

1.x fell back to the `TRUNK_API_KEY` and `TRUNK_BASE_URL` environment variables while these were unknown. 2.0 refuses an unknown value, because the credential decides which API the provider uses. If one comes from a resource not created yet, apply that resource first, for example with `-target`.

### `base_url` is the API host

Set it to the host, such as `https://api.trunk.io`. A value ending in `/v1`, as 1.x used, still works.

## New in 2.0

* **API keys.** See [Switch to an API key](#switch-to-an-api-key).
* **New settings:** `test_branch_construction_mode` and `batching_rules`.
* **New read-only attributes:** `queue_id` and `managed_state`, filled in when the provider uses an API key.
* **Import by queue ID**, with an API key.
* **Lower limits:**
  * `testing_timeout_minutes = 0` means no timeout.
  * With an API key, `batching_max_wait_time_minutes = 0` means don't wait.

See [Terraform Provider](./terraform) for the full reference.

## Switch to an API key

The organization API token uses the v1 API, which will be deprecated soon. To move to the v2 API:

1. An organization admin creates an API key under **Settings** → **Developer** → **API Keys**, with the **Update Merge Queue settings** permission. See [Create an API key](/merge-queue/reference/api-v2/authentication#create-an-api-key).
2. Replace the token with the key, in `TRUNK_API_KEY` or `api_key`.
3. Run `terraform plan`. It's empty: nothing else in the configuration changes, and `queue_id` and `managed_state` fill in on the next refresh.

The v2 API caps some values that v1 doesn't, for example `concurrency` at 1000 and `not_ready_timeout_hours` at 720. If your configuration sets a value above a cap, lower it before switching.

## Checklist

* [ ] The version constraint is `~> 2.0`, and `terraform init -upgrade` ran.
* [ ] `required_statuses = []` is set wherever you relied on leaving it out to clear an override.
* [ ] References into `required_statuses` use `tolist()`.
* [ ] `api_key` and `base_url` are known at plan time.
* [ ] `terraform plan` shows no unexpected changes.
