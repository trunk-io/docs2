title: "Skip single variations of a matrix job"

By default, Dynamic CI decides a matrix job as a whole: every variation runs, or
none does. You can opt a matrix job in to being decided by variation instead.
Dynamic CI then learns each group of variations from its own history, and a pull
request runs only the variations it is likely to break.

## When to opt in

A matrix job is a good fit when:

- **Its variations do different work.** Each runs on a different OS, runtime
  version, test suite or package group, so a change can break one and not the
  others.
- **It is expensive.** Skipping part of it saves real runner time.

Leave a job whole when its variations divide the same work differently on every
run. Dynamic CI can only learn from a variation's history if that variation does
the same work each time (see below).

Dynamic CI always decides these GitHub Actions matrices as one unit:

- **An axis whose values come from an expression**, such as
  `shard: ${{ fromJSON(needs.plan.outputs.shards) }}`. Write the values as a
  list, or have the planner job pass whole rows that the matrix reads at
  `include:`.
- **`include:` rows from an expression beside axes.** Have the planner write
  every variation as a full row, and remove the axes.
- **A literal fallback that declares axes**, such as
  `fromJSON(... || '{"os":["ubuntu-latest","macos-14"]}')`. Write the fallback as
  `include:` rows instead.

## Choose the keys to group by

This is the choice that matters most. You pick one or more of the matrix's keys.
Variations that share values for those keys form a **decision group**, and each
group gets its own run or skip decision, learned from that group's own history.

That history is only useful if each group does the **same work from one run to
the next**. If `suite=frontend` always runs the frontend tests, its history says
how often a change like this one breaks the frontend tests. If it runs a
different set of tests each time, its history says nothing, and its decisions
will be poor.

| Key | Good to group by? |
| --- | --- |
| OS, runtime version, image, test suite, package | Yes. The value names the work. |
| Shard number, when tests are assigned to shards deterministically (for example, a fixed list, or a split by file path) | Yes. Shard 2 runs the same tests on every run, and only changes when the tests themselves change. |
| Shard number, when shards are balanced by timing data or rebuilt on every run | No. Shard 2 runs different tests each time, so its history describes no particular work. |
| A value that is new on every run, such as a build number or commit SHA | No. Every run starts a new group with no history, so every variation always runs. **Group by** marks such a key **New value every run**. |

Some more guidance:

- **Keys you don't pick run together.** In a matrix of `os` × `node`, grouped by
  `os`, the Linux variations for every Node version run or skip together.
- **Fewer keys mean larger groups, which learn faster.** A group needs about 10
  runs in the past week before it is decided on its own history. Until then it
  follows the decision for the whole job.
- **Start with the key that names what breaks independently.** If the macOS build
  fails for reasons the Linux build never sees, group by OS.
- **A group passes only when every variation in it passed.** A run where a
  variation was skipped or missing does not count toward the group's history, so
  adding a key to the group shortens its history for a while.

## Opt a job in

<Steps>
  <Step title="Open the job's settings">
    In [Dynamic CI → Configuration](https://app.trunk.io/ci/dynamic-ci/configuration),
    open the **Jobs** tab and click the matrix job to expand it. A matrix job's
    **Schedule** column shows how it is grouped, such as **Group by none**.
  </Step>

  <Step title="Pick the keys under Group by">
    The **Matrix variations** section lists the job's variations under
    **Decision groups**. With no key picked, the job is one group,
    **All Variations**: every variation runs, or none does.

    Under **Group by**, click each key to group by. The list regroups as you go,
    one decision group for each value (or combination of values) of the keys you
    picked. Click a key again to unpick it. **View YAML** opens the workflow file
    with this job's matrix highlighted.
  </Step>

  <Step title="Set up your CI">
    - **GitHub Actions:** the matrix reads which variations to run from the
      Dynamic CI job. See [Matrix jobs on GitHub Actions](/ci/dynamic-ci/getting-started/github-actions#matrix-jobs).
    - **Buildkite:** no pipeline change beyond the plugin version. See
      [Matrix steps on Buildkite](/ci/dynamic-ci/getting-started/buildkite#matrix-steps).

    If the workflow on the default branch does not read the variations to run
    yet, the section says **The workflow needs a change before Dynamic CI can
    skip variations.** The **Matrix setup** card on the
    [Issues](https://app.trunk.io/ci/dynamic-ci/issues) tab then shows the
    change, with YAML you can copy. Every variation runs until the change is on
    the default branch. **Understanding variations** links to the setup steps
    for your matrix's shape.

    For a matrix Dynamic CI can't split (see [When to opt in](#when-to-opt-in)),
    the section says **Dynamic CI decides this job as one unit.** If the job is
    already grouped, click **Decide as one unit**: grouping it saves nothing.
  </Step>

  <Step title="Save">
    In an **Enforced** repository, the next push is decided by group. In
    **Learning** mode, Dynamic CI records a decision for each group and skips
    nothing, so you can see how the grouping would behave first.
  </Step>
</Steps>

To decide the job as one unit again, unpick every key under **Group by** and save.

Settings still apply to the whole job: **Always Run** and
[Force Run](/ci/dynamic-ci/force-run) run every variation, and a
[path filter](/ci/dynamic-ci/configuration/path-filters) applies to every group.
