The Dynamic CI Buildkite plugin decides at **pipeline-upload time**. Your pipeline is piped
through the plugin on its way to `buildkite-agent pipeline upload`, Trunk returns a verdict
per step, and the plugin adds a `skip:` attribute to the steps it recommends skipping — so a
skipped step never acquires an agent.

<Info>
  The plugin lives beside the GitHub Action in
  [`trunk-io/dynamic-ci`](https://github.com/trunk-io/dynamic-ci), so both speak one wire
  contract and ship on one release process.
</Info>

## Before you start

- **Buildkite telemetry is reaching Trunk.** Dynamic CI reasons over the CI history Trunk
  collects from Buildkite's OpenTelemetry export — see
  [Trunk CI → Buildkite](/ci/get-started/buildkite). A pipeline Trunk has no history for
  gets no verdicts.
- **The pipeline's git remote resolves to a repository Trunk knows.** Buildkite tells Trunk
  nothing about which repository a build belongs to except its remote, and the plugin parses
  `owner/name` out of `BUILDKITE_REPO` exactly the way ingestion did. If the two disagree,
  no repository is found and the build runs unfiltered.
- **Your steps have `key:` values.** Trunk identifies a Buildkite step by its declarative
  key — the only identity that stays stable as labels and matrix values change. A step
  without one always runs, and the plugin says which ones those were.
- **Dynamic CI is enabled for your organization,** and you have an organization API token.
  In the Trunk app, navigate to **Settings** → **Manage Organization** → **Organization API
  Token**.
- **The agent can run the plugin.** It needs `bash`, `curl` and `buildkite-agent`. It ships
  its own verified `jq` binary for linux-amd64, linux-arm64 and macos-arm64 and installs
  nothing; on any other platform it says so and uploads your pipeline unchanged.

## Set it up

<Steps>
  <Step title="Give your steps keys">
    ```yaml
    - key: unit-tests # required for Trunk to decide about this step
      label: ":test_tube: Unit tests"
      command: make test
    ```
  </Step>

  <Step title="Expose the token to the upload step">
    Put the organization API token where the step can read it — Buildkite `secrets:`, or
    your agent's own environment — and name the variable with `token-env` (default
    `TRUNK_TOKEN`).

    <Warning>
      **Never put the token in plugin configuration or an `env:` value.** Both are
      interpolated into the uploaded pipeline and shown in the Buildkite UI.
    </Warning>
  </Step>

  <Step title="Pipe your pipeline through the filter">
    The plugin's only contribution in the default `filter` mode is to put
    `trunk-dynamic-ci-filter` on your `PATH` for the duration of the step. It reads a
    pipeline on stdin — JSON or YAML — and writes one on stdout.

    ```yaml
    steps:
      - label: ":pipeline: upload"
        secrets:
          - TRUNK_TOKEN
        command: |
          cat .buildkite/pipeline.yml \
            | trunk-dynamic-ci-filter \
            | buildkite-agent pipeline upload
        plugins:
          - https://github.com/trunk-io/dynamic-ci.git/dynamic-ci-buildkite-plugin#main: ~
    ```

    A generated pipeline is identical, and does less work — a pipeline that is already JSON
    is never re-rendered:

    ```yaml
      command: |
        ./ci/emit-pipeline.sh \
          | trunk-dynamic-ci-filter \
          | buildkite-agent pipeline upload
    ```

    <Note>
      **Do not add `--no-interpolation` to your `pipeline upload`.** For a YAML pipeline the
      filter renders without interpolation, so your upload performs the single pass. If it
      does not, nothing interpolates and `$$VAR` reaches the shell, which reads `$$` as its
      own process id — `$$FOO` becomes something like `206FOO`. Not an error and not a
      blank: a plausible string that changes every run. The plugin warns when there is
      something to lose.
    </Note>
  </Step>

  <Step title="Run a build and read the log">
    The plugin names every step it marked:

    ```text
    --- :trunk: Dynamic CI marked 2 step(s) to skip
        unit-tests — passed on the last 40 runs; no correlated paths changed
        lint — no correlated paths changed
    ```

    Skipped steps stay visible in the build under **Show skipped steps**, with the
    recommendation's reason on hover. In
    [learning mode](/dynamic-ci/configuration#repository-mode) nothing is marked at all —
    the verdicts are recorded, and your pipeline uploads unchanged.
  </Step>
</Steps>

<Note>
  **Referencing the plugin.** The short form `trunk-io/dynamic-ci#v1` does not resolve yet
  during the beta, so reference the plugin by its full path as above. Pin the ref you want —
  `#main` tracks the latest, a release tag pins a version.
</Note>

## Every keyed step is a candidate

This is the one place the plugin differs in spirit from the GitHub Action. On GitHub Actions
you opt a job in by writing an `if:`. Here, once the plugin is on your upload step, **every
step with a `key:` is something Trunk may decide to skip.** There is nothing per-step to
wire up — which is convenient, and also means a step you never want skipped needs saying so.

```yaml
plugins:
  - https://github.com/trunk-io/dynamic-ci.git/dynamic-ci-buildkite-plugin#main:
      exclude-keys: deploy-master,publish-release
```

`exclude-keys` keeps a step out of Trunk's reach entirely — it still runs, Trunk just never
decides about it. Good for deploys, release gates, and anything whose cost of being wrongly
skipped is high.

For a standing policy rather than pipeline configuration, set the job to **Never skip** on
the repository's Dynamic CI configuration in the Trunk web app. Same effect, kept with the
rest of your Dynamic CI settings, and it survives someone editing the YAML.

## Trialling it on one step

Narrow the plugin to the steps you name, and leave the rest of the pipeline untouched:

```yaml
plugins:
  - https://github.com/trunk-io/dynamic-ci.git/dynamic-ci-buildkite-plugin#main:
      only-keys: e2e
```

This is the way to start small. The named step is marked **before it is dispatched**, so it
reports as genuinely skipped and no agent is acquired for it.

## Step mode

Step mode puts the plugin on a single step, which then asks about itself. Reach for it when
your pipeline lives entirely in Buildkite's settings editor and there is no upload step to
attach to — otherwise prefer `only-keys` above, which gets you a real skip.

```yaml
- key: e2e
  label: ":robot: E2E"
  command: make e2e
  secrets:
    - TRUNK_TOKEN
  plugins:
    - https://github.com/trunk-io/dynamic-ci.git/dynamic-ci-buildkite-plugin#main:
        mode: step
```

Two honest differences from filter mode, because the step has already been dispatched by the
time Trunk is asked:

- **The saving is smaller.** The agent is acquired, the repository checked out and plugins
  set up before anything is skipped. On a long step that is still most of the cost; on a
  short one it may be nearly all of it.
- **Buildkite reports the step as passed, not skipped**, because it ran and did no work.

A step in this mode **must** have a `key:` — it is the whole request — and the plugin fails
the step rather than running it if one is missing, so you never get a step that looks
filtered but is not.

## Options

| Option           | Default       | Description                                                                                                                                    |
| ---------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `mode`           | `filter`      | `filter` puts `trunk-dynamic-ci-filter` on `PATH` for your pipe; `step` decides about one individual step.                                          |
| `token-env`      | `TRUNK_TOKEN` | Name of the environment variable holding your organization API token. Never the token itself.                                                      |
| `only-keys`      | unset         | Comma-separated step keys to consider. Every other step runs untouched. Works in both modes.                                                        |
| `exclude-keys`   | unset         | Comma-separated step keys to never skip. Applied after `only-keys`, so a key in both is excluded.                                                   |
| `ignore-signals` | unset         | Comma-separated [signal identifiers](/dynamic-ci/how-it-works#the-signals) to drop from the tally.                                                  |
| `debug`          | `false`       | Print the requested step keys, the request body and the plan to the build log in collapsed groups. All of it goes to stderr, so it is safe in filter mode. |

`TRUNK_PUBLIC_API_ADDRESS` points the plugin at another Trunk deployment; it is the same
variable the test-results uploader and the GitHub Action read.

## What it does to your pipeline, and what it does not

The plugin's only effect is to add a `skip:` attribute to the steps Trunk recommended
skipping. Specifically, it:

- **Never reads or writes a file in your repository.** The pipeline is rendered by
  `buildkite-agent pipeline upload --dry-run --format json`, so your YAML is parsed by
  Buildkite's own agent and the change happens to the rendered copy in flight.
- **Never changes a command**, adds a step, removes a step, or reorders anything.
- **Never overrides a `skip:` you wrote yourself**, including `skip: false`.
- **Leaves a step the plan did not name completely unchanged.**

The whole mutation is seven lines of `jq`, kept small on purpose: it is the only part of the
plugin that changes what your build does.

## It fails open

Any failure — an unreachable API, a timeout, a plan this version cannot read, a missing `jq`
— uploads your pipeline **byte for byte unmodified** and logs why. This step is on the
critical path of every build; the plugin will not be what breaks one.

## Working out why nothing skipped

Set `debug: true` and the plugin prints three collapsed groups: the step keys it asked
about, the request body it sent, and the plan it got back. Between them they answer most
questions — whether your steps were seen, whether the repository and pipeline resolved to
what you expected, whether `baseSha` came out null, and what Trunk actually decided. None of
it contains your token, which travels in a request header.

More in [Troubleshooting](/dynamic-ci/troubleshooting).

<Warning>
  **Enforcement and Buildkite.** The `required-check` signal matches GitHub's
  `{workflow} / {job}` check-run shape, which a Buildkite pipeline's statuses never satisfy,
  so it abstains — and the merge-gate backstop that forces required jobs to run does not
  fire. Talk to us before enforcing Dynamic CI on a Buildkite pipeline, so the naming is
  mapped first.
</Warning>
