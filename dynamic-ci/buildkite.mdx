<Warning>
  Dynamic CI is in **private beta**, and your organization has to be enabled for
  it before the settings below appear — reach out on
  [Slack](https://slack.trunk.io) if they do not. Recommendation quality is still
  improving, the signals behind a verdict still change between releases, and the
  plugin's options are not yet stable. Pin an exact tag, and read the release
  notes before upgrading.
</Warning>

On Buildkite, Dynamic CI runs as a plugin:
[`trunk-io/dynamic-ci-buildkite-plugin`](https://github.com/trunk-io/dynamic-ci-buildkite-plugin).

It decides at **pipeline-upload time**, which is the whole point — a step it
skips never acquires an agent, so you pay nothing for it. The plugin contributes
one command, `trunk-dynamic-ci-filter`, which you pipe your pipeline through on
its way to `buildkite-agent pipeline upload`. It reads a pipeline on stdin and
writes one on stdout, adding a `skip:` attribute to the steps Trunk recommended
skipping and changing nothing else.

Your repository is never touched. The pipeline is rendered by Buildkite's own
agent (`pipeline upload --dry-run --format json`) and the change happens to that
rendered copy in flight.

## Before you start

Dynamic CI reasons from your repository's own CI history, so the history has to
be arriving before the plugin has anything to decide with.

<Steps>
  <Step title="Set up Trunk CI for the repository">
    Follow [Set up Trunk CI](/ci/get-started) and then
    [Set up Trunk CI for Buildkite](/ci/get-started/buildkite). By the end the
    repository exists in Trunk, has **CI Intelligence** on, and Buildkite is
    exporting OpenTelemetry traces to Trunk. The notification service export is
    enough on its own; agent tracing adds detail.

    Buildkite tells Trunk nothing about which repository a build belongs to
    except its **git remote**, which Trunk parses into `owner/name` and matches
    against a repository in your organization. Dynamic CI supports remotes on
    **github.com** only; a GitLab, Bitbucket or GitHub Enterprise remote is
    refused and the pipeline uploads unchanged.

    Give the history time to accumulate. A step needs a couple of weeks of
    regular builds before Trunk will recommend skipping it, and a step Trunk has
    never seen always runs.
  </Step>

  <Step title="Install the Trunk CI GitHub App on the repository">
    The plugin does **not** send your changed file set. Trunk fetches the diff
    between the base commit and the build's commit through the
    [Trunk CI](/setup/integrations/github/trunk-ci) GitHub App. Without it, the
    diff-derived signals have nothing to read.
  </Step>

  <Step title="Get your organization API token">
    In the Trunk app, navigate to **Settings** → **Organization** → **General**
    and copy the **API Token**. The same token your Buildkite OpenTelemetry
    export already uses works here.
  </Step>

  <Step title="Check the agent can run the plugin">
    The upload step's agent needs `bash`, `curl`, `git`, `awk` and either
    `sha256sum` or `shasum`. The plugin ships its own checksum-verified static
    `jq` for linux-amd64, linux-arm64 and macos-arm64 and installs nothing; on
    any other platform it says so and uploads your pipeline unchanged.
  </Step>
</Steps>

## Add the plugin

Pipe your pipeline through the filter. This works whether your pipeline is a
static file or generated by a script:

<CodeGroup>
```yaml Static pipeline file
steps:
  - label: ":pipeline: upload"
    secrets:
      - TRUNK_TOKEN
    command: |
      cat .buildkite/pipeline.yml \
        | trunk-dynamic-ci-filter \
        | buildkite-agent pipeline upload
    plugins:
      - trunk-io/dynamic-ci#v0.1.1: ~
```

```yaml Generated pipeline
steps:
  - key: upload-pipeline
    label: ":pipeline: build + upload"
    secrets:
      - TRUNK_TOKEN
    command: |
      ./ci/emit-pipeline.sh \
        | trunk-dynamic-ci-filter \
        | buildkite-agent pipeline upload
    plugins:
      - trunk-io/dynamic-ci#v0.1.1: ~
```
</CodeGroup>

<Note>
  **Pin an exact tag, v0.1.1 or later.** Buildkite agents cache a plugin
  checkout by the ref you name, and `BUILDKITE_PLUGINS_ALWAYS_CLONE_FRESH` is off
  by default — so moving a tag does not reach an agent that already has it. Use
  one exact release from
  [Releases](https://github.com/trunk-io/dynamic-ci-buildkite-plugin/releases),
  or a full commit SHA. Not a major alias, and not `#main`. v0.1.0 does not
  report builds in the form Trunk needs to detect false skips.
</Note>

### Keep the token out of the pipeline

Two things are interpolated into the uploaded pipeline and shown in the
Buildkite UI: plugin configuration, and `env:` values. Put the token in neither.

Expose it to the step through Buildkite `secrets:` or your agent's own
environment, and point `token-env` at the variable's name (it defaults to
`TRUNK_TOKEN`). The token travels in a request header, never in the request
body, so it does not appear in debug output either.

### Do not pass `--no-interpolation`

For a YAML pipeline the filter renders without interpolation, so your
`pipeline upload` performs the single interpolation pass. If it does not, nothing
interpolates and `$$VAR` reaches the shell, which reads `$$` as its own process
id — `$$FOO` becomes something like `206FOO`. Not an error and not a blank: a
plausible string that changes every run.

The plugin warns you when there is something to lose.

## Every step needs a `key:`

Trunk identifies a Buildkite step by its declarative `key:`. It is the only
identity that stays stable as labels and matrix values change, and it is what
Buildkite's OpenTelemetry export reports as the step's declaration — so the
`key:` in your pipeline is the same string the history is filed under.

```yaml
- key: unit-tests # <- required for Trunk to decide about this step
  label: ":test_tube: Unit tests"
  command: make test
```

A step without a key has no history to reason about, so it always runs. The
plugin names those steps in the build log rather than leaving you to guess.

Steps inside a `group:` are considered like any other. Two kinds of step behave
differently:

- **`trigger:` steps are never skipped.** Their outcome lives in the build they
  launch, so the plugin neither asks about them nor marks them.
- **Matrix and `parallelism:` steps share one key**, so a verdict covers every
  leg: the step runs in full or is skipped in full.

<Warning>
  **Every keyed step is a candidate.** This differs from how the GitHub Action
  works: once the plugin is on your upload step, every step with a `key:` is
  something Trunk may decide to skip. There is no per-step opt-in — which is
  convenient, and also means a step you never want skipped needs saying so.
</Warning>

## Nothing is skipped until the repository is enforcing

This is the one to check first when the plugin looks like it is doing nothing.

A repository in **Learning** mode is scored but never gated: the engine records
what it would have recommended and then serves every verdict as "run", so the
plugin marks nothing and your pipeline uploads unchanged. That is deliberate —
it is how you see what Dynamic CI would have done before it does it. Per-step
policies are not applied in Learning either, including **Always skip**.

In the Trunk app, navigate to **Dynamic CI** → **[your repository]**, then select
the mode from the **Dynamic CI mode** dropdown:

| Mode         | What happens                                                                          |
| ------------ | ------------------------------------------------------------------------------------- |
| **Learning** | Trunk scores every step and records the verdict. Nothing is ever skipped.             |
| **Enforced** | Trunk's verdicts are acted on — steps it votes to skip are marked and do not run.     |

Only an organization admin can change it. The mode is per repository, not per
CI provider: enforcing a repository enforces its GitHub Actions workflows and its
Buildkite pipelines alike.

<Warning>
  **Map your step policies before you enforce a Buildkite pipeline.** Two
  signals recognize a job that must pass to merge — `required-check` and
  `merge-queue-is-required` — and both read GitHub's `{workflow} / {job}`
  check-run shape, which a Buildkite pipeline never produces. On Buildkite they
  abstain.

  That is the safe reading, but it means the merge-gate backstop that would
  otherwise vote to run a required step does not fire here. Decide explicitly
  which steps must never be skipped, using the two mechanisms below, before
  turning enforcement on.
</Warning>

## Pull requests, the merge queue and other builds

Trunk puts each build in one of two lanes, and each lane has its own policies:

- **Merge queue** — a build on a `trunk-merge/` or `gh-readonly-queue/` branch.
  Nothing is skipped here unless you have configured a paths filter or set a
  step's merge-queue policy to **Always skip**.
- **Pull request** — every other build. That includes builds of your default
  branch and other branches with no pull request, which can be skipped too.
  If you never want a branch build skipped, keep the plugin off that pipeline's
  upload step for those branches.

Some things available on GitHub Actions do not reach Buildkite yet:

- Signals that read a pull request's own run history, such as
  `previous-result-on-pr`, have no data on Buildkite and abstain.
- **Force overrides** — forcing a job to run for one pull request from the Trunk
  app — list GitHub Actions workflows only.

## Trialling it on one step

Narrow the plugin to the steps you name and leave the rest of the pipeline
untouched. This is the way to start:

```yaml
- label: ":pipeline: upload"
  secrets:
    - TRUNK_TOKEN
  command: |
    cat .buildkite/pipeline.yml \
      | trunk-dynamic-ci-filter \
      | buildkite-agent pipeline upload
  plugins:
    - trunk-io/dynamic-ci#v0.1.1:
        only-keys: e2e
```

The named step is marked before it is dispatched, so it reports as genuinely
skipped and no agent is acquired for it.

## Steps that must never be skipped

Deploys, release gates, anything whose cost of being wrongly skipped is high.
Two ways to say so:

<Tabs>
  <Tab title="In the pipeline">
    `exclude-keys` keeps a step out of Trunk's reach entirely. It still runs;
    Trunk just never decides about it. Applied after `only-keys`, so a key in
    both is excluded.

    ```yaml
    plugins:
      - trunk-io/dynamic-ci#v0.1.1:
          exclude-keys: deploy-master,publish-release
    ```
  </Tab>

  <Tab title="In the Trunk app">
    In the Trunk app, navigate to **Dynamic CI** → **[your repository]** →
    **Configuration**, click your pipeline, and select **Always run** for the
    step. The default is **Automatic**, which leaves the decision with Dynamic
    CI; **Always run** and **Always skip** take the step off the engine, pinned
    on or off. Your pipeline appears there once Trunk has scored at least one of
    its builds.

    Policies are set per lane — pull requests and merge queue separately — since
    the same step can be worth skipping on a PR and mandatory in the queue.

    This is a standing policy rather than pipeline configuration, so it stays
    with the rest of your Dynamic CI settings and survives someone editing the
    YAML.
  </Tab>
</Tabs>

## Make sure the base commit resolves

The plugin derives the base commit itself, as the merge base of the pull
request's target branch and `HEAD`:

```sh
git merge-base "origin/$BUILDKITE_PULL_REQUEST_BASE_BRANCH" HEAD
```

If your checkout is shallow or single-branch — Buildkite's `git-clone-flags` and
`git-fetch-flags` decide this — `origin/main` may not exist in the working copy
and that command answers nothing. The request is still valid: `baseSha` goes out
as null, the plan still comes back, and you lose the diff-derived signals rather
than the whole thing.

It is quiet, so it is worth checking once with `debug: true`. If `baseSha` is
null on a pull request build, fetch the target branch before the upload step.

## What it does, and what it does not

The plugin's only effect is to add a `skip:` attribute to steps Trunk
recommended skipping.

- It **never reads or writes a file in your repository.**
- It **never changes a command**, adds a step, removes a step, or reorders anything.
- It **never overrides a `skip:` you wrote yourself**, including `skip: false`.
- A step the plan did not name is uploaded unchanged.

The whole mutation is
[seven lines of `jq`](https://github.com/trunk-io/dynamic-ci-buildkite-plugin/blob/main/lib/apply-skips.jq),
small on purpose: it is the only part of the plugin that changes what your build
does.

Skipped steps stay visible in the build — use **Show skipped steps** — with the
reason on hover. The log says the same thing in one place, naming every step it
marked:

```text
--- :trunk: Dynamic CI marked 2 step(s) to skip
    unit-tests — passed on the last 40 runs; no correlated paths changed
    lint — no correlated paths changed
```

Those reasons are the full ones, not the 70-character versions Buildkite shows
on the step.

## It fails open

Any failure — an unreachable API, a timeout, an error response, a plan this
version cannot read, a missing `jq` — uploads your pipeline unmodified and logs
why. This step is on the critical path of every build; the plugin will not be
what breaks one.

That is also why a step with no verdict runs. Fail-open is the default in every
direction: the cost of a failure is a full CI run, never a skipped test.

The one exception is a configuration mistake: an unrecognized `mode` fails the
step on its first build, rather than leaving a plugin that looks installed and
never decides anything.

## Troubleshooting

**Nothing is being skipped.** Check the repository's mode first — in Learning,
nothing ever is. Then check that your steps have `key:` attributes, and that
Trunk has history for them.

**The log shows a notice.** When Trunk returns a plan but has a reason to skip
nothing, the plugin prints the reason as a `--- :trunk:` line:

| Notice                    | Meaning                                                                                              |
| ------------------------- | ---------------------------------------------------------------------------------------------------- |
| `ORG_NOT_ENABLED`         | Dynamic CI is not enabled for your organization yet.                                                 |
| `REPO_NOT_ENABLED`        | Trunk has switched Dynamic CI off for this repository. Reach out on Slack.                          |
| `REPO_IN_SHADOW_MODE`     | The repository is in Learning mode (the message says "shadow mode"). Verdicts are recorded, nothing is skipped. |
| `WORKFLOW_NOT_RECOGNIZED` | Trunk has not yet seen a completed build of this pipeline with these step keys.                      |
| `ENGINE_UNAVAILABLE`      | Trunk could not produce a plan this time. Temporary; every step runs.                                |

**The log shows an HTTP error.** The plugin prints the status and the start of
the response body before uploading your pipeline unchanged:

- `401` — the token is missing or not recognized. Check `token-env`.
- `404 REPOSITORY_NOT_FOUND` — the remote did not match a repository with CI data
  in your organization. See below.
- `400 CI_HOST_UNSUPPORTED` — the remote is not on github.com.
- `400 VALIDATION_FAILED` — often an unknown identifier in `ignore-signals`.

**Turn on debug output.** Set `debug: true` and the plugin prints three collapsed
groups to the build log: the step keys it asked about, the request body it sent,
and the plan it got back.

```yaml
plugins:
  - trunk-io/dynamic-ci#v0.1.1:
      debug: true
```

Between them they answer most questions — whether your steps were seen, whether
the repository and pipeline resolved to what you expected, whether `baseSha` came
out null, and what Trunk actually decided. All of it goes to stderr, so it is safe
in filter mode, where stdout carries the pipeline being uploaded.

**The request body shows the wrong repository.** The `repo` in the body is parsed
from `BUILDKITE_REPO`, using the same rule CI ingestion used when it created the
repository this request resolves against. If the two disagree, the request
answers `404 REPOSITORY_NOT_FOUND`. Confirm the pipeline's remote matches the
repository in your Trunk organization, and that
[Trunk CI is receiving its builds](/ci/get-started/buildkite).

**A step you did not expect was skipped.** Set its policy to **Always run**, or
add its key to `exclude-keys`, and tell us — during the beta that feedback is how
the signals get tuned.

## If your pipeline lives in Buildkite's settings editor

**Step mode** puts the plugin on a single step, which then asks about itself.
Reach for it only when there is no upload step to attach to — otherwise prefer
`only-keys` above, which gets you a real skip.

```yaml
- key: e2e
  label: ":robot: E2E"
  command: make e2e
  secrets:
    - TRUNK_TOKEN
  plugins:
    - trunk-io/dynamic-ci#v0.1.1:
        mode: step
```

Two honest differences, because the step has already been dispatched by the time
Trunk is asked:

- **The saving is smaller.** The agent is acquired, the repository checked out,
  and plugins set up before anything is skipped. On a long step that is still
  most of the cost; on a short one it may be nearly all of it.
- **Buildkite reports the step as passed, not skipped**, because it ran and did
  no work.

A step in this mode must have a `key:` — it is the whole request — and the plugin
fails the step rather than running it if one is missing, so you never get a step
that looks filtered but is not.

`only-keys` and `exclude-keys` work in step mode too, so one shared plugin block
(a YAML anchor, say) can sit on many steps while the lists control which are live.

## Options

| Option           | Default       |                                                                                                                                                          |
| ---------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mode`           | `filter`      | `filter` puts `trunk-dynamic-ci-filter` on PATH for your pipe; `step` decides about one individual step.                                                  |
| `token-env`      | `TRUNK_TOKEN` | Name of the environment variable holding your Trunk organization API token. Never put the token in plugin configuration or an `env:` value.               |
| `only-keys`      | unset         | Comma-separated step keys to consider. Every other step runs untouched. Works in both modes.                                                              |
| `exclude-keys`   | unset         | Comma-separated step keys to never skip. Applied after `only-keys`, so a key in both is excluded.                                                         |
| `debug`          | `false`       | Print the requested step keys, the request body and the plan to the build log, in collapsed groups. All of it goes to stderr, so it is safe in filter mode. |
| `ignore-signals` | unset         | Comma-separated [signal](/dynamic-ci#how-a-verdict-is-reached) identifiers to exclude from the recommendation. An unknown identifier is an error, so a typo fails open loudly. |
