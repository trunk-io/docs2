<Warning>
  Dynamic CI is in **private beta**. Recommendation quality is still improving,
  the signals behind a verdict still change between releases, and the action's
  and plugin's inputs and outputs are not yet stable. Pin a specific tag if you
  need stability, and read the release notes before upgrading.
</Warning>

## What it is

Most CI runs are wasted. A docs-only change does not need the integration suite; a
frontend typo does not need the backend tests. The usual fix is a path filter —
hand-written globs that are coarse, go stale, and encode a guess about which files
matter to which job.

Dynamic CI answers the same question from evidence instead. Trunk already records every
`(file change set → job outcome)` pair in your repository, so it can tell you which jobs
this diff has historically broken and which it never touches. Before your jobs start,
Trunk returns a **verdict per job** — run or skip — with the signals behind it, and your
workflow gates on that verdict.

Nothing is pooled across customers. Every recommendation is derived only from your own
organization's CI history.

Both speak the same wire contract and the same engine, so a verdict does not depend on
which provider asked for it. What differs is where the decision lands: an `if:` you
write per job on GitHub Actions, and a `skip:` attribute added in flight on Buildkite.

## How it compares to a path filter

|                         | `dorny/paths-filter` and friends                        | Dynamic CI                                                                     |
| ----------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Where the rules live    | Globs you write and maintain                            | Signals measured on your repository, plus optional globs where you want them   |
| What it knows           | Which files changed                                     | Which files changed, what those files have historically broken, what the job costs, what already ran on this PR |
| When it goes stale      | Whenever the codebase moves and nobody updates the globs | It does not — the history moves with the repository                            |
| Why a job was skipped   | Because a glob did not match                            | A per-signal breakdown printed in the logs and recorded on the pull request     |
| Blast radius of a miss  | A silently untested job                                 | A false skip that is recorded, counted, and reported back to you               |

You do not have to choose. Dynamic CI has a `paths-filter` signal at parity with
`dorny/paths-filter`, so an existing glob rule can be kept as an explicit, deterministic
input to the verdict — see [Configuration](/dynamic-ci/configuration#paths-filters).

## What it needs

<Steps>
  <Step title="CI data flowing into Trunk">
    Dynamic CI reasons over the CI history Trunk already collects, so the repository
    needs **CI Intelligence** turned on and reporting. See
    [Trunk CI → Getting Started](/ci/get-started) for GitHub Actions and Buildkite
    ingestion.
  </Step>

  <Step title="Enough history to reason about">
    A job Trunk has not seen enough of gets no verdict and runs. Repositories arrive in
    **learning mode**, where Trunk records what it *would* have skipped without anything
    actually being withheld — which is both the trust on-ramp and how the history
    accumulates.
  </Step>

  <Step title="Something that gates your merges">
    A recommendation can be wrong. The safety argument is that the jobs which gate a
    merge still run somewhere — a [merge queue](/merge-queue/merge-queue), or required
    checks on the base branch. Trunk enforces this: on a branch whose merges are gated,
    required jobs are forced to run. See
    [How it works](/dynamic-ci/how-it-works#the-merge-queue-backstop).
  </Step>

  <Step title="Trunk to turn it on">
    Dynamic CI is enabled per organization during the private beta. Until it is, every
    request answers with a notice and every job runs. Reach out on
    [Slack](https://slack.trunk.io).
  </Step>
</Steps>

## What you get back

- **A verdict per job**, with the contribution of every signal that voted, printed in
  the job log and optionally posted as a run annotation.
- **A decision matrix per pull request** — the Dynamic CI tab on a PR shows every
  run/skip decision by job and commit, the signals behind the selected one, and any
  false skips.
- **Savings by repository and workflow** — compute saved, wall-clock saved (a separate
  number, because skipping ten parallel jobs saves ten jobs of compute and one job of
  waiting), runs skipped, and false skips. See [In the Trunk app](/dynamic-ci/in-the-app).
