Trunk Runners run your GitHub Actions jobs on Trunk's own bare-metal fleet. You
keep your workflows on GitHub and change one line, the `runs-on` label, to move a
job. Trunk Runners are built around three promises:

## Fast

### Faster hardware

Jobs run on bare-metal machines, not on shared cloud VMs. On the same job, a
Trunk runner is about 40% faster than a comparable AWS machine.

### Start ready with templates

Most CI time is spent before the first build step: installing toolchains,
pulling images, restoring dependencies. A [template](/runners/actions/templates-and-regions)
bakes that setup into the machine image, so a job starts with everything it
needs already in place. Setup that a cache can only speed up, a template
removes.

### Caches in the compute cluster

The Trunk shared cache runs in the same cluster as your jobs, and Trunk sets it
up for you with no workflow changes.

| Tool            | What you get                                                                        |
| --------------- | ----------------------------------------------------------------------------------- |
| `actions/cache` | About 275 MiB/s, against about 110 MiB/s on the GitHub cache, with similar latency. |
| Bazel           | The shared cache as Bazel's remote cache.                                           |
| sccache         | Rust builds through `sccache`, with the shared cache as storage.                    |
| Nix             | The shared cache as a Nix binary cache.                                             |

`actions/cache` support makes moving to Trunk Runners easy. Over time, move the
setup it restores into a template and skip the restore entirely. See
[Caching](/runners/cache/index).

## Reliable

- **Run by a platform team.** Trunk operates the fleet, the images, and the
  caches, so your team does not maintain self-hosted runners.
- **Priority for the branches that matter.** Mark your default branch, release
  branches, or merge queue branches as priority. When CI is busy, their jobs
  start first. See [Limits and priority](/runners/settings/limits-and-priority).
- **Nothing dropped under load.** When your organization reaches its CPU limit,
  Trunk holds new jobs and starts them as CPUs free up.
- **A fresh machine for every job.** Each job gets a new VM, which Trunk removes
  when the job ends. No state leaks from one job to the next.

## Affordable

- **Pay for what the job uses.** Compute is billed per vCPU minute and memory per
  GB minute. The default machine (2 CPUs, 8 GiB) costs $0.006 per minute. See
  [Pricing](/runners/pricing).
- **Size each job to fit.** Mix CPU count and memory per job, so a lint job does
  not pay for a build machine. See [Machine sizes](/runners/actions/sizes).
- **Run less CI.** Pair Trunk Runners with [Dynamic CI](/ci/dynamic-ci/index) to
  skip jobs that a change cannot affect. The cheapest job is the one that does
  not run.
- **See where the time goes.** Monitor CPU and memory use per job to find the
  right balance of cost and speed.

## How it works

You keep your workflows on GitHub. You change one thing: the `runs-on` label of a
job. That label tells Trunk to run the job. Trunk starts a VM, runs the job, and
removes the VM when the job ends.

## What you can configure

- **The runner** — the `runs-on` label sets the size you need and the template to
  start on. See [The runs-on label](/runners/actions/runs-on).
- **Caching** — choose which build tools use the shared cache, per repository or
  for the whole organization, and see what is cached. See
  [Caching](/runners/cache/index).
- **Organization defaults** — set a default template. See
  [Organization defaults](/runners/settings/ci-defaults).
- **Limits and priority** — set a CPU limit for CI and mark priority branches.
  See [Limits and priority](/runners/settings/limits-and-priority).
